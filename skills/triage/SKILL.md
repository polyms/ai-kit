# Triage

Move issues on the project issue tracker through a small state machine of triage roles.

If this repo treats external pull requests as a request surface (see [issue-tracker.md](../../docs/agents/issue-tracker.md)), triage covers them too: **a PR is an issue with attached code** — same roles, same states, same machine. Resolve a bare `#42` to an issue or PR per the tracker config.

Every comment or issue posted to the issue tracker during triage **must** start with this disclaimer:

```
> *This was generated by AI during triage.*
```

**Prerequisites:** Run `/setup` if `docs/agents/issue-tracker.md` or `docs/agents/triage-labels.md` is missing (ADR-0001 hard dependency).

## Roles

Read label strings from [docs/agents/triage-labels.md](../../docs/agents/triage-labels.md). Canonical roles:

**Category** (exactly one per triaged item):

- `bug` — something is broken
- `enhancement` — new feature or improvement

**State** (exactly one per triaged item):

- `needs-triage` — maintainer needs to evaluate
- `needs-info` — waiting on reporter for more information
- `ready-for-agent` — fully specified, ready for an AFK agent
- `ready-for-human` — needs human implementation
- `wontfix` — will not be actioned

For a PR, the same states read against the attached code: `ready-for-agent` means a brief is attached and an agent should take the next step on the diff; `ready-for-human` means it's ready for a human to merge.

If state roles conflict, flag it and ask the maintainer before doing anything else.

**Transitions:** An unlabeled issue normally goes to `needs-triage` first; from there it moves to `needs-info`, `ready-for-agent`, `ready-for-human`, or `wontfix`. `needs-info` returns to `needs-triage` once the reporter replies. The maintainer can override at any time — flag unusual transitions and ask before proceeding.

## Natural language requests

The maintainer invokes `/triage` and describes what they want in natural language. Interpret the request and act. Examples:

- "Show me anything that needs my attention"
- "Let's look at #42" (issue or PR)
- "Move #42 to ready-for-agent"
- "What's ready for agents to pick up?"

## Show what needs attention

Query the issue tracker and present three buckets, oldest first:

1. **Unlabeled** — never triaged
2. **`needs-triage`** — evaluation in progress
3. **`needs-info` with reporter activity since the last triage notes** — needs re-evaluation

```bash
gh issue list --json number,title,labels,createdAt,updatedAt
gh issue list --label <needs-triage-mapped-string> --json number,title,labels,createdAt
```

Substitute mapped label strings from `docs/agents/triage-labels.md`, not canonical role names.

When PRs are in scope, include external PRs in these buckets and tag each line `[PR]` or `[issue]`. Discovery surfaces only _external_ PRs (the tracker config defines who counts as external) — a collaborator's in-flight PR is not triage work. This filter is discovery-only; an explicitly named PR is always triaged regardless of author.

Show counts and a one-line summary per item. Let the maintainer pick.

**Completion criterion:** Three buckets presented with counts; maintainer selects an item or gives a different direction.

## Triage a specific issue or PR

### 1. Gather context

Read the full issue or PR (body, comments, labels, author, dates; for a PR, the diff too). Parse any prior triage notes — if resuming, check whether the reporter answered outstanding questions; don't re-ask resolved ones.

```bash
gh issue view <number> --comments
gh pr view <number> --comments   # when PR is in scope
```

Explore the codebase using glossary vocabulary from `CONTEXT.md`, respecting ADRs in the area. Run two checks:

- **Redundancy** — search for an existing implementation by domain concept (not just the request's wording); report where you looked. If found → already-implemented `wontfix` (step 5).
- **Prior rejection** — read `.out-of-scope/*.md` per [out-of-scope.md](out-of-scope.md) and surface any match.

**Completion criterion:** Full issue/PR read; prior triage notes parsed; redundancy and out-of-scope checks reported.

### 2. Recommend

Tell the maintainer your category and state recommendation with reasoning, plus a brief codebase summary — including whether it's already implemented. Wait for direction.

**Completion criterion:** Maintainer confirms or redirects category and target state.

### 3. Verify the claim

Before any grilling, check that the claim holds up. For a bug, reproduce from the reporter's steps. For a PR, confirm the diff does what it claims — check it out, run relevant tests or commands. Report: confirmed (with code path), failed, or insufficient detail (strong `needs-info` signal). A confirmed verification makes a stronger agent brief.

**Completion criterion:** Verification result reported; confirmed bugs/enhancements have a concrete code path or repro.

### 4. Grill (if needed)

If the request needs fleshing out, reach **`align-loop`** and **`domain-modeling`** together — design tree, one question, A–D + `(Recommended)`, codebase-first; sharpen domain terms and update `CONTEXT.md` inline as decisions land. Question shape: [GRILL-FORMAT.md](../align-loop/GRILL-FORMAT.md). Do not duplicate those skill bodies here; follow them in-process.

**Completion criterion:** Request is specific enough for an agent brief, or maintainer chooses to stop at `needs-info`.

### 5. Apply the outcome

Apply **one category** and **one state** label using mapped strings from `docs/agents/triage-labels.md`. Remove conflicting state/category labels when replacing:

```bash
gh issue edit <number> --add-label "<category>" --add-label "<state>" --remove-label "<old-state>"
gh issue comment <number> --body "..."
gh issue close <number>    # for wontfix
```

| State             | Action                                                                                                                            |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `ready-for-agent` | Post agent brief comment ([agent-brief.md](agent-brief.md))                                                                       |
| `ready-for-human` | Same structure as agent brief; note why it can't be delegated (judgment calls, external access, design decisions, manual testing) |
| `needs-info`      | Post triage notes (template below)                                                                                                |
| `wontfix`         | Close with comment depending on _why_ (see below)                                                                                 |
| `needs-triage`    | Apply the role; optional comment if partial progress                                                                              |

**`wontfix` variants:**

- **Already implemented** — point to where it lives; do **not** write to `.out-of-scope/`
- **Rejected (bug)** — polite explanation, then close
- **Rejected (enhancement)** — write to `.out-of-scope/`, link from comment, then close ([out-of-scope.md](out-of-scope.md))

**Completion criterion:** Category and state labels applied on tracker; comment posted with disclaimer; issue closed if `wontfix`.

## Quick state override

If the maintainer says "move #42 to ready-for-agent", trust them and apply the role directly. Confirm what you're about to do (role changes, comment, close), then act. Skip grilling. Apply category label too if missing. If moving to `ready-for-agent` without a grilling session, ask whether they want to write an agent brief.

**Completion criterion:** Requested state applied; maintainer confirmed the action plan.

## Needs-info template

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

Capture everything resolved during grilling under "established so far" so the work isn't lost. Questions must be specific and actionable, not "please provide more info".

## Handoff to `/dev`

When an issue reaches `ready-for-agent` with an agent brief attached, end with `## Next Step` pointing to `/dev` and the issue number.

**Completion criterion:** `## Next Step` names `/dev` and the ready issue when applicable.
